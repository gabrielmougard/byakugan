# Model2Vec in C, on ggml

**Question.** Can Model2Vec run behind a true C API, as fast as possible? model2vec-rs depends on Rust's `tokenizers` and `safetensors` crates; can ggml stand in for them? And which potion model should we run, given that most of the pages we crawl are not English?

**Short answer.**
- **ggml covers two of the three needs:**
  - **The file format.** It can't read safetensors, but its own format, GGUF, now holds each model's table and its whole tokenizer in one mmapped file.
  - **The maths.** It does SIMD matrix multiplies on the CPU. Taxonomy similarity, the costly part, is now one `mul_mat` per page.
- **ggml has no tokenizer, so we wrote ours in C.** They are ports of model2vec-rs's WordPiece and Unigram paths, plus Hugging Face's SentencePiece charsmap normaliser. On 1,133,527 texts per model, they give exactly the token ids of Hugging Face `tokenizers`, with 0 mismatches. The texts are real English, French, German, Italian and Spanish pages, edge cases, random strings, and every Unicode code point.
- **Faster:** a whole page profile (all four presets and segment labels, no T4) takes 8.5 ms instead of 56.3 ms on English pages (6.6×), and 19.7 ms instead of 103.3 ms on other languages (5.2×). The similarity step alone dropped from 357 ms to 2 ms per page.
- **Two models, routed by language:**
  - **potion-base-32M** for English pages: the strongest static English model.
  - **potion-multilingual-128M** for every other language, or when none is declared: 101 languages.

  On French, German and Italian news, the "Style & Fashion > Personal Care" false positive is gone.
- **Smaller:** Q8_0 tables shrink the models from 123 MB to 34 MB and from 489 MB to 143 MB. Loading both takes 0.2 s and 91 MB of memory, since the tables are mmapped.

Measured 2026-11-06 on an Apple M4, one core. The Raspberry Pi measurement is pending: the cluster was unreachable from this network.

## 2. Why GGUF and not a safetensors reader

A safetensors reader is easy: an 8-byte length, a JSON header, raw tensors. The problem is the tokenizer, which lives in `tokenizer.json`, a format only Hugging Face code reads in full. Converting once to GGUF puts everything in one file:

| Key | Content |
|---|---|
| `m2v.tokenizer` | `wordpiece` or `unigram` |
| `m2v.tokens`, `m2v.unk_id` | the vocabulary, by id |
| `m2v.added_tokens`, `m2v.added_ids` | tokens matched literally before normalisation (`[PAD]`, `[UNK]`, `[CLS]`…) |
| `m2v.wordpiece.prefix`, `.max_chars` | `##`, 100 |
| `m2v.unigram.scores` | float64, as Hugging Face's Viterbi uses them |
| `m2v.unigram.charsmap` | SentencePiece's precompiled normalisation map, as bytes |
| `m2v.unigram.isolate` | the ASCII characters padded with spaces |
| tensor `embeddings` | the table, Q8_0 by default (`--type f16` or `f32` also work) |

The C side then needs no JSON parser. Loading reads the keys with ggml's GGUF API, builds a byte trie of the vocabulary, and mmaps the table. Q8_0 keeps one byte per value plus a scale per 32 values: the multilingual table goes from 512 MB to 136 MB, and ggml dequantises each row as it is read.

## 3. Exactness

**The token ids must match Hugging Face's, or the embeddings are not the model's.** The pipelines, in order:

| WordPiece (potion-base-32M) | Unigram (potion-multilingual-128M) |
|---|---|
| added tokens matched in the raw text | the same |
| BertNormalizer: drop controls, CJK padded, NFD, accents stripped, lowercase | SentencePiece charsmap, applied per grapheme cluster |
| BertPreTokenizer: split on whitespace, punctuation isolated | 33 ASCII punctuation characters padded, whitespace collapsed, stripped |
| WordPiece: greedy longest match, `##` continuations, unknown word = `[UNK]` | Metaspace (`▁`), then Viterbi over 500,353 scored pieces, unknown runs fused |

**Unicode tables taken from the reference itself.** HF's BERT normaliser decides "control or unassigned" with the `unicode_categories` crate, which dates from 2016. So characters assigned since are deleted rather than tokenised, and no current Unicode release reproduces that. `gen_m2v_tables.py` therefore asks `tokenizers` how it normalises and pre-tokenises each of the 1.1M code points, and writes the answers as range tables (160 KB). Hangul syllables decompose by arithmetic instead of 11,172 table entries.

**Graphemes.** HF's charsmap normaliser runs over grapheme clusters: a cluster under 6 bytes is replaced as a whole, keeping the replacement of its shortest mapped prefix. So the cluster boundaries change the output. They follow UAX #29 for Unicode 16.0, the version the `unicode-segmentation` crate implements, including the Indic conjunct rule.

**The check.** For each model, the expected ids came from HF `tokenizers` 0.22.1, and the C tokenizer was compared with them:

| Set | Texts | Mismatches (base-8M, base-32M, multilingual) |
|---|---|---|
| segments of 36 English pages, and each page whole | 7,528 | 0, 0, 0 |
| segments of 31 French, German, Italian, Spanish pages, and each page whole | 10,813 | 0, 0, 0 |
| edge cases (model2vec-rs's lists and more) | 122 | 0, 0, 0 |
| random strings over 21 Unicode blocks | 3,000 | 0, 0, 0 |
| every code point between two letters, `a<c>b` | 1,112,064 | 0, 0, 0 |

Fed the wrong model's expectations, the same harness reports mismatches on nearly every text, so it is not passing by accident. The committed fixtures (722 synthetic texts per model) keep the check in `dune test`. To rerun the full set, use `m2v_fixtures.py --all`.

## 4. Speed

| Per page, Apple M4, one core | Before (OCaml, potion-base-8M) | After (C + ggml) |
|---|---|---|
| Similarity of every segment with 704 prototypes | 357 ms | 2.0 ms (256 dimensions), 3.7 ms (512) |
| Whole profile, English pages | 56.3 ms | 8.5 ms (6.6×) |
| Whole profile, French, German, Italian, Spanish pages | 103.3 ms | 19.7 ms (5.2×) |

- **Tokenising is not the bottleneck.** WordPiece runs at 28 MB/s and Unigram at 6 MB/s, about 1 ms for a typical page.
- **The win is the similarity step.** It was 704 dot products per segment, over OCaml lists; it is now one matrix multiply per page with NEON on ARM.
- **On the Pis,** pages cost 2.1 CPU-seconds each, and T2 was most of that. A 5–7× drop would move the cluster's CPU ceiling (4.2 pages a second) well above what politeness and T4 allow. To be measured.

## 5. Which model, for which page

| Model | Languages | Tokenizer | Table | GGUF (Q8_0) |
|---|---|---|---|---|
| potion-base-32M | English (from bge-base-en-v1.5) | WordPiece, 63,091 tokens | 63,091 × 512 | 34 MB |
| potion-multilingual-128M | 101 (from bge-m3) | Unigram, 500,353 tokens | 500,353 × 256 | 143 MB |

**Routing.**
- The page's `<html lang>`, else `og:locale`.
- `en`, `en-*` and `en_*` go to potion-base-32M.
- Everything else, including pages that declare nothing, goes to the multilingual model, which reads English too.

**Calibration.** The Platt constants that turn a cosine into a probability were set by hand for potion-base-8M. On the same English pages, both new models give segment cosines within 0.01 of it (median and 90th percentile). So the constants are kept, one pair per text length, shared by both models. The multilingual model's page-level cosines run lower (median 0.41 against 0.49), which makes it more conservative on page labels. Fitting one pair per model on the golden set is M2 work.

**First look at quality**, top `rich` labels on pages that used to read "Deodorant":
- **gala.de**, a celebrity magazine: Pop Culture > Celebrity.
- **gazzetta.it**: Sports.
- **de.euronews**, on Israel and Iran: Politics, plus a conflict-related Sensitive Topic.
- **il Post**, Italian news: no T2 label above 0.5. T4 and the lexicon do the rest.

This is a spot check, not a measurement; the golden set decides.

## 6. Caveats

- **No truncation.** Python Model2Vec truncates to 512 tokens by default; we embed all of the text, as the OCaml version did.
- **Canonical reordering edge.** It runs on the marks that survive accent stripping. A run separated by a combining grapheme joiner could reorder differently from NFD. Nothing in 1.1M texts hit it.
- **Prototypes are English for both models.** They are built from taxonomy names and English lexicon terms. Reviewed lexicons in five languages would add native-language terms.
